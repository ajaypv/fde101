Offline evals provide evidence for a production-readiness decision; they do not prove readiness by themselves. Production evidence also includes authorization and privacy tests, operational limits, online monitoring, drift detection, and user outcomes.

## Begin with the denominator

Suppose the top three retrieved documents are:

```text
refund-policy        relevant
pricing              not relevant
security             not relevant
```

Two documents are known to be relevant: `refund-policy` and `cancellation-policy`.

- **Precision@3 = 1 / 3**: one relevant result divided by the requested `k` of three.
- **Recall@3 = 1 / 2**: one relevant result found divided by two known relevant results.

Written as formulas:[^ranked-metrics]

```text
Precision@k = relevant results in the first k / k
Recall@k    = relevant results in the first k / all known relevant results
```

This book calculates Precision@k only when the retriever returned at least `k` results. If it returned fewer, record an incomplete result or rerun with a valid `k`; silently changing the denominator makes comparisons misleading. Recall@k also needs a trustworthy set of known relevant passages. Test questions with no relevant evidence belong in a separate unanswerable-question and abstention suite.

## Keep retrieval and generation separate

A final answer can look good even when retrieval was weak, and strong retrieval can still be followed by a bad answer. Score the two parts separately so a failure points to the component that needs work.

| Layer | Metric | Compares | Question it answers |
| --- | --- | --- | --- |
| Retrieval | Precision@k | Top `k` passages vs relevance labels | How clean is the retrieved list? |
| Retrieval | Recall@k | Top `k` passages vs all known relevant passages | Did retrieval find the needed evidence? |
| Retrieval | MRR | Reciprocal of the first relevant rank, averaged across queries | Did at least one useful result appear early? |
| ANN index | ANN recall@k | Approximate top `k` IDs vs exact top `k` IDs | How closely does the fast index match exact vector search? |
| Generation | Faithfulness or groundedness | Answer claims vs retrieved context | Does the supplied evidence support each claim? |
| Generation | Answer relevance | Answer vs user question | Did the response address what was asked? |
| Generation | [Correctness](../glossary/answer-correctness/) | Answer vs trusted reference | Does the answer agree with known truth? |

LangSmith documents these as distinct comparison pairs rather than one blended “RAG quality” score.[^rag-eval] RAGAS likewise evaluates retrieval, faithful use of context, and generation quality as separate dimensions.[^ragas]

## Flight delay: two jobs, two failure points

Use a small case before building a large dashboard. The policy below is **fictional**; it teaches evaluation and does not describe any airline's actual rules.

```text
Passenger: My flight is delayed by six hours. Am I eligible for a free hotel?

Gold policy: Hotel accommodation is provided only when both conditions hold:
1. the delay requires an overnight stay; and
2. the airline caused the delay.

Reference answer: A six-hour delay alone does not establish eligibility.
Ask whether an overnight stay is required and whether the airline caused the delay.
```

The RAG system must pass two different tests:

| Run | Hit@3 | Retrieval result | Generated answer | Generation result |
| --- | --- | --- | --- | --- |
| Retrieval failure | `0` | Precision@3 = `0 / 3`; Recall@3 = `0 / 1` | Not graded in this isolated stage test | The generator never received the evidence it needed |
| Generation failure | `1` | Precision@3 = `1 / 3`; Recall@3 = `1 / 1` | “Yes. A six-hour delay qualifies.” | Relevant to the question, but unfaithful and incorrect |
| Passing run | `1` | Precision@3 = `1 / 3`; Recall@3 = `1 / 1` | “Six hours alone is not enough; both policy conditions must hold.” | Faithful, relevant, and correct |

The denominators tell different stories:[^ranked-metrics]

- Precision@3 divides the relevant retrieved items by **3 returned positions**.
- Recall@3 divides the relevant retrieved items by **1 known relevant policy**.
- Hit@3 asks only whether at least one relevant item appeared. Here it has the same pass/fail value as Recall@3 because the case has exactly one known relevant policy. The metrics differ when several passages are relevant.

The answer labels also compare different evidence:[^rag-eval]

- **Faithfulness** compares answer claims with retrieved context. “Six hours qualifies” is unsupported by the policy.
- **Answer relevance** compares the answer with the passenger's question. The wrong “yes” still addresses the question, so it can be relevant but incorrect.
- **Correctness** compares the answer with the reviewed reference answer. The reference says six hours alone is insufficient.

## One question, four different failures

```text
Question: What is the return window?

Retrieved context:
- Returns are accepted for 30 days.
- The company was founded in 1998.

Trusted reference: The return window is 30 days, and a receipt is required.
```

| Generated answer | Grounded? | Relevant? | Correct? | Diagnosis |
| --- | --- | --- | --- | --- |
| “Returns are accepted for 30 days.” | Yes | Yes | Yes | Supported, direct, and matches the reference |
| “Returns are accepted for 30 days without a receipt.” | No | Yes | No | The receipt claim lacks context support and contradicts the trusted reference |
| “The company was founded in 1998.” | Yes | No | No | Supported by context, but it does not answer the question |
| “Returns are accepted for 60 days.” | No | Yes | No | It addresses the question but contradicts the evidence and reference |

A grounded answer can still be wrong when the indexed source is stale. A correct answer can be ungrounded when the model supplies a fact that the retrieved context never supported. Keep both checks.

## Compare versions with the same test

Suppose the baseline uses a chunk size of 500, `k = 5`, embedding model A, and no reranker. A candidate changes chunking, adds a reranker, or switches to embedding model B. Those settings describe the experiment; they do not prove improvement.

Freeze the questions, corpus and permission snapshot, `k`, query transforms, generation settings, reference answers, evaluator version, and release thresholds. If chunking changes, freeze gold source spans or answer-bearing units and map each candidate's chunks back to them; chunk IDs and boundaries are not stable labels.

Then run both versions and record the measured results:

| Check | Baseline | Candidate | Decision rule |
| --- | --- | --- | --- |
| Recall@5 | measured value | measured value | Candidate must meet the retrieval gate |
| Precision@5 | measured value | measured value | Candidate must not fill context with noise |
| Faithful answer rate | measured value | measured value | Candidate must meet the grounded-answer gate |
| Correct answer rate | measured value | measured value | Review every high-impact regression |
| p95 latency and cost/query | measured value | measured value | Candidate must stay within operating limits |

Do not copy a claim such as “recall rose from 70% to 90%” into a design document unless that exact result came from this system's versioned eval set. Report absolute values, percentage-point deltas, dataset size, paired regressions, and uncertainty. Keep a held-out release set so repeated tuning does not overfit the evaluation.

If chunking, embeddings, and reranking all change together, the experiment supports a claim about the **candidate bundle**. Change one factor at a time or run ablations before attributing the gain to a specific component. LangSmith's official RAG tutorial follows the same core workflow: create a dataset, run the application, and score the results.[^rag-eval]

[MRR](../glossary/mrr/) ignores relevant items after the first, so it does not replace Recall@k for multi-passage answers. **ANN recall@k** is a different denominator again: it measures overlap with exact vector neighbors, not human relevance. High ANN recall can faithfully reproduce a poor embedding ranking.

## Evaluate each stage

| Stage | What to measure | Example failure |
| --- | --- | --- |
| Ingestion | parse coverage, freshness, metadata | Tables disappear during extraction |
| Retrieval | recall@k, precision@k, rank | Correct policy never reaches the context |
| Answer | groundedness, correctness, completeness | Answer contradicts retrieved evidence |
| Citation | source validity and claim support | Link exists but does not support the sentence |
| Behavior | abstention, tool choice, policy compliance | Model guesses when evidence is absent |
| Operations | latency percentiles, cost, error rate | Quality passes but p95 latency misses the SLA |

## Build the dataset before the dashboard

A useful first dataset can be small:

1. collect real questions from users and support staff;
2. include ordinary, multi-passage, exact-identifier, unanswerable, and adversarial cases;
3. label acceptable evidence and answer behavior;
4. preserve dataset versions;
5. inspect failures individually before averaging scores.

Use human-reviewed examples to calibrate automated judges. An LLM grader is another model with possible errors, not an objective measuring instrument.

## Turn a metric into a gate

Define the decision before running the evaluation. These thresholds are illustrative; choose them from the workflow's risk and baseline:

```text
Release only if:
  # Retrieval quality
  retrieval recall@5 >= 0.90
  retrieval precision@5 >= 0.70

  # Answer behavior
  grounded answer rate >= 0.95
  reference-answer correctness >= 0.90
  correct abstention rate >= 0.90
  supported citation rate >= 0.95

  # Safety
  unauthorized passage exposure == 0
  critical prompt-injection successes == 0

  # Operations
  p95 latency <= 4 seconds
  p95 cost per answer <= agreed budget
  request error rate <= agreed SLO
```

An average cannot excuse a critical data-isolation failure. Safety gates are hard stops; quality and operational thresholds express the product trade-offs. A writing assistant and an invoice approval agent should not share the same gate.

## FDE questions

- What user decision could a wrong answer change?
- Which failures are severe even if the average score is high?
- Does the test set represent each customer, language, permission level, and source type?
- Can a reviewer trace a failing score back to input, retrieval, model output, and code version?
